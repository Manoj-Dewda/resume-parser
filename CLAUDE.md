# Resume Parser — Project Rules

## What this is
A resume parsing and search engine. Extracts structured data from resumes
(PDF/DOCX), stores it, and provides hybrid keyword + semantic search.
Candidate-facing: shows people how a parser actually reads their resume.

## Hard constraints — do not violate

### Zero cost
Every service must have a permanent free tier. Approved:
- LLM + embeddings: Google Gemini free tier
- Database: Supabase or Neon (Postgres + pgvector)
- Frontend hosting: Vercel Free (Next.js only)
- Backend hosting: Render Free (Web Service) — runs `api/` and
  `worker/` together in one service, since Render has no free instance
  type for its separate Background Worker service type. See
  `docs/DEPLOY.md` for the startup command and why this is one service,
  not two. Oracle Cloud was evaluated and explicitly rejected —
  repeated deployment attempts there were unreliable, and it is not an
  approved option, not even as an alternative.
- CI: GitHub Actions (public repo)

No Redis. No paid APIs. No AWS services that bill.
If a task seems to need a paid service, stop and tell me — don't work
around it silently.

### No real personal data, ever
Only synthetic resumes generated by us. Free-tier LLM providers may train
on inputs. Never commit anything resembling a real person's data.

### Architecture boundaries
- `packages/parser/` is a pure Python library. No FastAPI, Next.js, or
  database imports. It takes bytes, returns a Pydantic model.
- Queue is a Postgres table using `SELECT ... FOR UPDATE SKIP LOCKED`.
- Web layer never calls the LLM directly; it enqueues a job.

### Every parser change gets measured
No prompt or extraction logic change is "done" until `eval/score.py` runs
and reports field-level accuracy. Show me the before and after numbers.
If accuracy drops, say so plainly.

## Stack
Python 3.12, uv, ruff, pytest, Pydantic v2, FastAPI, Next.js, Tailwind.

## Build order — do not skip ahead
1. Repo skeleton + synthetic corpus generator
2. Parser library
3. Eval scorer + baseline accuracy number
4. Postgres schema + job queue
5. API
6. UI
7. Deploy

The web app comes last. Do not scaffold a frontend before step 6.

## Working style
- One slice at a time. Stop and let me review before moving on.
- Ask before installing a dependency.
- Don't create files I didn't ask for. No placeholder or TODO stubs.
- When something is ambiguous, ask rather than assume.
